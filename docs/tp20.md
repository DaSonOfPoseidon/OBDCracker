# VW TP2.0

VW TP2.0 is the transport VAG's older modules use to carry KWP2000 on CAN. It has no public standard. The layouts
below come from hobbyist descriptions and traces of VAG modules. On the A7 only the channel setup and disconnect are
confirmed so far, by the passenger door (52) in session 6 (#124), so the decoders in
`crates/obdcracker-core/src/tp20.rs` check every length, opcode and ID exactly.

## Frames

Every frame is up to 8 data bytes on an 11-bit CAN ID. The first byte is the opcode (channel setup frames start with
an address instead).

**Channel setup** is sent to CAN ID `0x200`. The module answers on `0x200` plus its address.

| Frame | Bytes |
|---|---|
| Request | `<address> C0 00 10 00 03 01` |
| Positive reply | `00 D0 <tester RX ID> <tester TX ID> 01` |
| Refusal | `00 <D6, D7 or D8> <5 more bytes>` (application not supported, no resources, not ready); the decoder needs the full 7 bytes |

- In the request, the module's own IDs are left to it (`00 10`: the high byte's bit 4 marks an ID as not given), and
  the tester proposes to be answered on `0x300` (`00 03`). The last byte, `01`, is the KWP2000 application.
- Each ID in a reply is two bytes: the low byte, then the high byte's low 3 bits (11-bit IDs). Any other bit in the
  high byte, the invalid flag included, is malformed. So is an ID in `0x200..=0x2FF` (the setup range), the same ID
  for both directions, or a receive ID other than the `0x300` the request proposed.
- The reply's first ID is the one the tester receives on (the module sends on it), and the second is the one the tester
  sends on. For example `00 D0 00 03 40 07 01`: the module sends on `0x300` and listens on `0x740`.

**Channel parameters** (`A0` from the tester, `A1` from the module):

```
A1 <block size> <T1> <T2> <T3> <T4>
```

- Block size is how many data frames the sender may send before it needs an ACK, 1 to 15 (the byte's low nibble).
  Anything else is malformed.
- T1 is how long the sender waits for an ACK. T3 is the gap it wants between frames sent to it. T2 and T4 are read
  but unused.
- A time byte is a unit in its top two bits (0.1, 1, 10 or 100 ms) and a count in the low six; `FF` means not given.
  T1 and T3 must be given. The tester's own parameters are block size 15, T1 100 ms (`8A`) and T3 5 ms (`32`).

**Data frames** carry a message of up to 65535 bytes. The opcode's high nibble says whether more frames follow and
whether the sender waits for an ACK; the low nibble is the sequence number, 0 to 15, wrapping:

| High nibble | Meaning |
|---|---|
| `0` | more frames follow; ACK wanted after it |
| `1` | last frame of the message; ACK wanted |
| `2` | more frames follow; no ACK |
| `3` | last frame of the message; no ACK |

A message's first frame starts with its 2-byte big-endian length, then data. Only a message's last frame is marked, so
after a bad frame that isn't last, the receiver drops every frame up to and including the next last one, whatever its
bytes. A message of 5 bytes or fewer fits one frame (`MAX_SINGLE_FRAME`), and the tester always asks for an ACK:
`10 00 02 1A 9B` is the 2-byte message `1A 9B`. A receiver rejects a length of 0, a length over its buffer, data past
the length, and a last frame that ends before the length.

## ACK and keep-alive

- An **ACK** is one byte: `B<n>` says the receiver is ready for the frame with sequence number `n`; `9<n>` says it is
  not ready, and the frames wait. The tester acks a module's frame that asks for one with the next sequence number
  (`(sequence + 1) mod 16`), and the module's sequence numbers go on across messages.
- **Keep-alive** is `A3`. The module answers with its channel parameters (`A1`), which keeps the channel open.
- **Disconnect** is `A8`. The module answers with `A8`.

## Channels

`obdcracker_transport::tp20::probe` looks for VW TP2.0 modules: it sends a channel setup to each address in turn and
closes each channel a module opens. Reading on a channel is [`ChannelSession`](#data-transfer).

- Every address's setup is approved by the policy before the first is sent, so a refused address, or one given
  twice, sends nothing (`FingerprintError::Rejected`). Each disconnect is approved just before it's sent.
- A timeout to a setup only means nothing is there, so the address is left out. An adapter failure is an error.
- A module's answer is a channel (`Answer::Channel`), a refusal with its opcode, such as 0xD7 for no resources
  (`Answer::Refused`), or bytes that couldn't be decoded (`Answer::Undecodable`).
- For a channel, the disconnect goes to the channel's own IDs, which come from the module's reply. The policy only
  approves a disconnect to IDs taken from the expected setup reply (`Policy::tp20_channel`); otherwise nothing is sent
  and the result is `Disconnect::NotSent` with the rejection. Only a policy narrowed with the modules' `ModuleIds`
  also refuses IDs that belong to another module, which the unnarrowed `Policy::read_only()` can't tell.
- `Disconnect::Closed` means the module answered the disconnect. `Disconnect::NoReply` means it didn't answer in time,
  which is harmless: a module closes an idle channel by itself.

## Data transfer

`obdcracker_transport::tp20::ChannelSession` reads KWP2000 on a channel of its own (#142):

- **Opening:** `ChannelSession::open` sends the channel setup, then the tester's parameters (`A0`), and keeps the
  module's (`A1`). A channel that gets no parameters is closed again.
- **Requests:** `request` sends a KWP2000 request as one data frame (at most 5 bytes, `MAX_SINGLE_FRAME`) with the
  next sequence number, asking for an ACK. The policy checks it against the KWP2000 allowlist and tiers, as it checks
  any KWP2000 request (`Policy::approve_tp20_request`); a refused request sends nothing and leaves the channel open.
- **Answers:** the module ACKs the request's frame (`B<n>`, its next sequence number), then sends its answer in data
  frames. The session ACKs each frame that asks for one, and returns the answer once a whole message answers the
  request (`response::kwp2000_answers`): positive, or a refusal. Response-pending (`7F <service> 78`) is waited
  through for P2*, at most `Timing::max_pending` times. Each frame from the module restarts the wait, which is the
  longer of P2 and the module's T1.
- **Errors close the channel.** A frame that breaks the framing (a sequence number out of order, as when the adapter
  lost one; an ACK of a frame the tester didn't send, or a second one; a frame with no place there), a message that
  answers another request, or no answer in time means replies may be out of step, so the session sends `A8` and every
  later request gets `ChannelError::Closed`. A module that sends `A8` itself has closed it.
- **Keep-alive:** after 500 ms without a frame (`KEEP_ALIVE_IDLE`), the next request is preceded by `A3`, which the
  module answers with its parameters. `keep_alive` sends one on demand.
- **Closing:** `close` sends `A8` and says how the module took it; dropping the session sends it too, without a report.
- **Bounds:** every wait is bounded by time the module can't extend (frames from other IDs don't restart it) or by a
  count of frames (`MAX_FRAMES_PER_MESSAGE` per message, as many messages as `max_pending` allows).

What a module does between frames, and how fast, is what car session 7 (#169) checks: the ACK timing through an ELM
adapter is in [elm327.md](elm327.md#vw-tp20-channel-frames).
