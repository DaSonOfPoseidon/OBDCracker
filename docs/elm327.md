# ELM327 notes

What the `elm` driver (`crates/obdcracker-transport/src/elm/`) relies on, with the page of the ELM327 datasheet
(ELM327DS v2.0, Elm Electronics) each fact comes from. STN chips (`OBDLink` adapters) accept the same commands.
Check a claim here against the datasheet before changing the driver because of it.

## Safety

- **A line of hex digits is a bus request** (p. 7), sent as pairs of digits (p. 29). `AT` commands are recognised by
  their `AT` prefix, and the adapter ignores spaces and control characters anywhere in a line (p. 8). A serial line
  can flip a bit: `ATE0` with its `T` flipped to `D` is `ADE0`, a two-byte request. So no single flipped bit in any
  command the driver writes, its carriage return included, may leave a line of hex digits; a test flips every bit of
  every command. That rules out commands whose only non-hex letter is the `T` of `AT` (`ATE0`, `ATCAF1`, `ATCFC1`,
  `ATCF700`).
- **The adapter echoes every line** (echo is on after a reset, p. 9). The driver leaves it on and checks that each
  echo matches what it wrote; anything else means the adapter heard something else, and the driver stops. For an
  `AT` command that's before anything reaches the bus (a misheard `AT SH` would aim the next request at another
  module). For a request the adapter has already sent what it heard by then, so the driver can only stop.
- **Programmable parameters change the defaults** (`AT PPS`, p. 57). The driver relies on four defaults instead of
  sending the commands for them: echo (PP 09, p. 59), CAN auto formatting and CAN flow control (PP 24 and 25), and no
  data length between a frame's CAN ID and its data (PP 29, p. 61). It reads the summary after the reset and refuses
  an adapter where any of them is on with another value, or missing from the summary. `PPS` and all four parameters
  arrived together in v1.1 (the version history in ELM327DS v2.1, p. 90), and STN chips list them too (OBDLink FRPM,
  section 7.3), so a missing one means the summary was cut short. An adapter that answers `?` has no parameters and is
  at the factory defaults.
- **A bare carriage return repeats the last command** (p. 8). That could be another program's request, so the driver
  never writes an empty line, not even to wake the adapter up.
- **Any character interrupts the adapter** while it's working (pp. 7, 47). It prints `STOPPED` and a prompt, and the
  interrupting character may be lost or kept. The driver never interrupts: it waits for the prompt, and if none comes
  it treats the adapter's state as unknown and refuses to write anything more.
- **Automatic protocol search sends probe frames**: during a search the adapter ignores the headers it was given and
  sends standard requests such as `01 00` on each protocol's default IDs (`AT SP 0`, and `AT SP A6` when its own
  attempt fails; p. 36). Those frames come from the adapter, not from an approved request, and no audit log records
  them. The driver sets protocol 6 (ISO 15765-4 CAN, 11-bit IDs, 500 kbit/s) without the `A`.
- **A reset adapter is back at its defaults** (echo on, headers off, and possibly automatic protocol search). It says
  `LV RESET` after a brownout, and `ERR94` (a fatal CAN error) needs a full reset that restores the defaults (p. 79).
  The driver stops using an adapter that prints either, any other `ERRxx`, `LP ALERT`, `SEARCHING...` or `UNABLE TO
  CONNECT` ("tried all of the available protocols", p. 80: it only searches if it lost protocol 6; the other cause, a
  failed ISO 14230 initiation on p. 19, doesn't apply to CAN), an overlong line (which could hide any of these), or
  anything it doesn't expect, such as a banner, or `STOPPED` (the driver never interrupts the adapter, so something
  else did, and the interrupting byte may start the next line). It checks this wherever it reads the adapter's output,
  including output it's only draining, and anything printed after a prompt: the adapter says nothing between its
  prompt and the next line it's sent, so before each write the driver checks that nothing has arrived. It reads for 1
  ms, past any stray NUL. A reset whose first byte is still on its way then can't be seen before the write; the checks
  on the reply catch it after (a reset adapter has headers off, and may say `SEARCHING...`). Since a banner always
  means a reset, the adapter's ID comes from the banner it printed when the driver reset it, not from `AT I`.
- **The adapter sends ISO-TP flow control frames itself** (`CFC1`, p. 48). They aren't approved requests and
  aren't in the audit log. In flow control mode 0 the adapter uses the ISO 15765-4 frames meant for the OBD-II IDs.
  The datasheet doesn't say which ID mode 0 uses for other modules, so for anything other than 0x7DF and
  0x7E0..=0x7E7 the driver uses mode 1, which sends `30 00 00` to the module's request ID (`AT FC SH`, `FC SD`,
  `FC SM 1`; mode 1 refuses to start until the header and data are set, p. 48). The adapter answers any first
  frame that passes its receive filter, so with the wide filter below, a module that sends a multi-frame message
  while we talk to another one gets a flow control frame meant for that other module.

## Output format

- With `ATH1` and `ATS1` each received frame is a line: the 3-digit CAN ID, then the data bytes, **PCI byte
  included** (p. 46). With headers off the adapter strips the PCI and prints `0:`, `1:` segment lines instead, so
  the driver turns headers on and reassembles with `obdcracker-core`'s ISO-TP reassembler.
- Replies from several ECUs may interleave (p. 45), so the driver reassembles each CAN ID separately.
- Lines end with a carriage return, plus a line feed if `ATL1` is set; the prompt is `>` (p. 7). The UART may insert
  stray NUL bytes (p. 8).
- Status and error messages are listed on pp. 78-80. A frame that failed a check is printed with ` <DATA ERROR` or
  ` <RX ERROR` after it.

## Timing

- After a request the adapter waits up to `AT ST` x 4 ms for the first reply, and the same again after each reply
  for more (p. 26). The maximum, `AT ST FF`, is about 1 s. With adaptive timing (`AT AT1`, p. 12) the adapter
  learns shorter waits, never longer than `AT ST`.
- The datasheet says nothing about response-pending replies (`7F xx 78`). The adapter stops listening after its
  timeout like after any reply, so a module that takes longer than about 1 s after a response-pending reply looks
  like a timeout.
- `AT Z` takes about a second (p. 47).
- The serial link is slow next to the bus: an ELM327 starts at 9600 or 38400 baud (p. 7). A 4095-byte reply is 586
  frame lines of up to 29 characters, about 18 s at 9600 baud, so the driver's P2, its P2* after response-pending, and
  its wait for a request to finish allow for that on top of their usual times. A working adapter ends each request
  with its prompt, which ends the wait at once; only a hung one makes the driver wait it out.

## Receive filter

- By default the adapter picks a receive filter from the header (`AT AR`, pp. 11-12), which the datasheet doesn't
  define for every header. The driver sets a filter that passes every 11-bit ID from 0x700 to 0x7FF
  (`AT CRA 7XX`, where `X` means any digit, p. 14), and `exchange` decides which replies count. A frame from any other
  ID means the adapter lost the filter, and the driver stops. `X` digits arrived in ELM327 v2.0 (ELM327DS v2.1, p. 90);
  STN chips accept them too (OBDLink FRPM, `ATCRA pattern`), though they report themselves as v1.4b. A genuine older
  ELM327 or a clone that answers `?` is refused at connect. The older alternatives aren't safe: `AT CF 700` has a
  single non-hex letter, and `AT CRA hhh` + `AT CM 700` leaves an `M` that one flipped bit turns into a carriage
  return.

## Limits

- With auto formatting on, a request is one single frame of up to 7 bytes (p. 46). The driver refuses longer
  requests before writing anything. That covers the OBD-II reads and UDS 0x22 with up to 3 DIDs, but not every
  request the read-only policy allows: 0x22 with 4 DIDs is 9 bytes.
- A first frame's 12-bit length allows replies of up to 4095 bytes (p. 46).
