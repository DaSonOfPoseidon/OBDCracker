# ELM327 notes

What the `elm` driver (`crates/obdcracker-transport/src/elm/`) relies on, with the page of the ELM327 datasheet
(ELM327DS v2.0, Elm Electronics) each fact comes from. STN chips (`OBDLink` adapters) accept the same commands.
Check a claim here against the datasheet before changing the driver because of it.

## Safety

- **A line of hex digits is a bus request** (p. 7), sent as pairs of digits (p. 29). `AT` commands are recognised by
  their `AT` prefix, and the adapter ignores spaces and control characters anywhere in a line (p. 8). A serial line
  can flip a bit: `ATE0` with its `T` flipped to `D` is `ADE0`, a two-byte request. So no single flipped bit in any
  command the driver writes, its carriage return included, may leave a line of hex digits; a test flips every bit of
  every command. That rules out commands whose only non-hex letter is the `T` of `AT` (`ATE0`, `ATCAF1`, `ATCFC1`,
  `ATCF700`), except when they're written the way a request is: the raw-mode switch for VW TP2.0 (below).
- **The adapter echoes every line** (echo is on after a reset, p. 9). The driver leaves it on and checks that each
  echo matches what it wrote; anything else means the adapter heard something else, and the driver stops. For an
  `AT` command that's before anything reaches the bus (a misheard `AT SH` would aim the next request at another
  module). A request is checked before it can reach the bus too, on adapters that echo as they read (next item).
- **A request's echo is checked before its carriage return** (#34). The adapter echoes each character as it arrives
  and acts on a line only at its carriage return. Measured on the OBDLink EX (STN2232 v5.12.4, #54): each character
  echoes within 3 to 15 ms, and a line without a carriage return is **held indefinitely**, not discarded after about
  20 s as the ELM327 datasheet describes; the next carriage return, whenever it comes, sends it. So the driver writes a
  request's digits, waits up to 1 s for all of them to echo, and writes the carriage return only if they match. On
  a mismatch or a missing echo it writes `XX` and a carriage return instead, so the adapter refuses the line with `?`
  and nothing reaches the bus, then stops. No single flipped bit of `XX\r` leaves a line of hex digits (one `X`
  survives any flip; a test checks every bit). An adapter that echoes nothing before the carriage return on the first
  request (a clone that echoes whole lines, or ELM327-emulator) is taken to echo only whole lines: from then on its
  echo is checked after the carriage return, as before #34, and the accepted risk below applies to it in full.
- **A flipped bit in a request is an accepted risk** (#19), now only on an adapter that echoes whole lines (above), and
  for a flip on the way back that hides one on the way in. The host link has no checksum: STN chips have no
  checksummed or framed host mode (OBDLink FRPM rev. f: the UART is 8N1 with no parity). One flipped bit can change a digit, or drop it: the adapter ignores control
  characters (p. 8) and reads a trailing odd digit as a response count (ELM327DSJ p. 32), so `22 F1 87` can arrive as
  `2F 18 7`. It's accepted rather than prevented because:
  - USB carries a CRC up to the adapter, so on a USB adapter such as the OBDLink EX the only unchecked hop is the
    board-level UART between its USB chip and the STN, where bit errors are very rare. On a Wi-Fi adapter the radio's
    frame check and TCP's checksum cover the radio link, leaving the same board-level UART. A direct RS-232 or TTL serial
    connection (also supported by `--serial`) has no such check, and its unchecked UART includes the whole cable, so
    the risk is higher there; prefer a USB or Wi-Fi adapter.
  - One corrupted frame can't brick a module. Reprogramming takes a sequence (programming session, security access
    with a computed key, download, transfer, exit) that no single frame completes, and a module that wrongly enters a
    session times out back to the default one. A corrupted frame can still be any single request one flip away,
    including ones the policy locks or bans: a reset, clearing DTCs (`01 47` with its `1` dropped is mode `04`), one
    write (`22 EA BC …` → `2E AB CD 03`), or starting an on-board test (`09 xx` → `08 xx`). Most are refused by the
    module, but not all.
  - The driver checks every echo and stops at the first mismatch, so a corrupted request is never followed by
    another one.

  Refusing every request with a dangerous one-bit neighbour was tried and dropped (PR #31): it refused most mode 01
  PIDs, every UDS `22` read (one flip from KWP2000's stop-routine `32`) and every mode 09 read (one flip from mode
  08). #29 records a misheard request in the audit log.
- **Programmable parameters change the defaults** (`AT PPS`, p. 57). The driver relies on four defaults instead of
  sending the commands for them: echo (PP 09, p. 59), CAN auto formatting and CAN flow control (PP 24 and 25), and no
  data length between a frame's CAN ID and its data (PP 29, p. 61). It reads the summary after the reset and refuses
  an adapter where any of them is on with another value, or missing from the summary. `PPS` and all four parameters
  arrived together in v1.1 (the version history in ELM327DS v2.1, p. 90), and STN chips list them too (OBDLink FRPM,
  section 7.3), so a missing one means the summary was cut short. An adapter that answers `?` has no parameters and is
  at the factory defaults.
- **A bare carriage return repeats the last command** (p. 8). That could be another program's request, so the driver
  never writes an empty line, not even to wake the adapter up.
- **Any character interrupts the adapter** while it's working (pp. 7, 47). It prints `STOPPED` and a prompt, and the
  interrupting character may be lost or kept. The driver interrupts in two cases only: a frame on an open TP2.0
  channel sent while the adapter still listens, and stopping a monitor it started (see
  [VW TP2.0 channel frames](#vw-tp20-channel-frames)). Otherwise it waits for the prompt, and if none comes it treats
  the adapter's state as unknown and refuses to write anything more.
- **Automatic protocol search sends probe frames**: during a search the adapter ignores the headers it was given and
  sends standard requests such as `01 00` on each protocol's default IDs (`AT SP 0`, and `AT SP A6` when its own
  attempt fails; p. 36). Those frames come from the adapter, not from an approved request, and no audit log records
  them. The driver sets protocol 6 (ISO 15765-4 CAN, 11-bit IDs, 500 kbit/s) without the `A`, and switches to protocol
  7 (the same with 29-bit IDs, `AT SP 7`) and back only when a request's target needs the other width. A 29-bit header
  is set in two parts: its top 5 bits with `AT CP` and the rest with `AT SH` and six digits. Every one of these keeps
  at least two non-hex letters, so no single flipped bit makes it a bus request. A switch forgets the header, flow
  control and filter, which are set again for the new width.
- **29-bit flow control goes to the request ID** (`AT FC SH` with eight digits, mode 1). The adapter's own (mode 0) is
  built from the reply's ID by swapping its address bytes, which suits ISO 15765-4's `0x18DAF1xx` but sends VAG's
  `0x17FE00xx` replies' flow control to an ID no module listens on, so the module would stop after its first frame.
- **A reset adapter is back at its defaults** (echo on, headers off, and possibly automatic protocol search). It says
  `LV RESET` after a brownout, and `ERR94` (a fatal CAN error) needs a full reset that restores the defaults (p. 79).
  The driver stops using an adapter that prints either, any other `ERRxx`, `LP ALERT`, `SEARCHING...` or `UNABLE TO
  CONNECT` ("tried all of the available protocols", p. 80: it only searches if it lost protocol 6; the other cause, a
  failed ISO 14230 initiation on p. 19, doesn't apply to CAN), an overlong line (which could hide any of these), or
  anything it doesn't expect, such as a banner, or `STOPPED` outside the two interrupts above (anything else that
  stopped the adapter did so, and the interrupting byte may start the next line). It checks this wherever it reads
  the adapter's output, including output it's only draining, and anything printed after a prompt: the adapter says nothing between its
  prompt and the next line it's sent, so before each write the driver checks that nothing has arrived. It reads for 1
  ms, past any stray NUL. A reset whose first byte is still on its way then can't be seen before the write; the checks
  on the reply catch it after (a reset adapter has headers off, and may say `SEARCHING...`). Since a banner always
  means a reset, the adapter's ID comes from the banner it printed when the driver reset it, not from `AT I`.
- **The adapter sends ISO-TP flow control frames itself** (`CFC1`, p. 48). They aren't approved requests and
  aren't in the audit log. In flow control mode 0 the adapter uses the ISO 15765-4 frames meant for the OBD-II IDs.
  The datasheet doesn't say which ID mode 0 uses for other modules, so for anything other than 0x7DF and
  0x7E0..=0x7E7 the driver uses mode 1, which sends the driver's data to the module's request ID (`AT FC SH`,
  `FC SD`, `FC SM 1`; mode 1 refuses to start until the header and data are set, p. 48). A physical request to an
  OBD-II ECU uses mode 1 too when the driver paces the module (see Timing), and mode 0 when it doesn't. The data is
  continue-to-send with no block limit: `30 00 xx`, where `xx` is the gap. A broadcast always uses mode 0: each
  answering ECU needs flow control on its own request ID (0x7E8's on 0x7E0), and mode 1 has one fixed header.
  Mode 2 doesn't help: its chart says the adapter provides the ID bits, but the text says they're the First
  Frame's own, unchanged (p. 48), so 0x7E8's flow control would go to 0x7E8 and the ECU would never continue. The adapter answers any first
  frame that passes its receive filter, so with the wide filter below, a module that sends a multi-frame message
  while we talk to another one gets a flow control frame meant for that other module. The driver narrows the filter
  to the one reply ID whenever the request knows it, which avoids that (#16).

## Setup

After `AT Z` the driver sends these, in this order, and each must answer `OK`. A `?` or anything else is fatal (see
Clones).

| Command | Why |
|---|---|
| `ATL0`, `ATS1`, `ATH1` | Linefeeds off; spaces and headers on, so every frame line shows its CAN ID and PCI byte (Output format). |
| `ATSP6` | ISO 15765-4 CAN, 11-bit IDs, 500 kbit/s, never automatic search (Safety). |
| `ATR1` | Wait for replies after every request. |
| `ATCRA7XX` | Show every 11-bit reply ID from 0x700 to 0x7FF until a request narrows the filter (Receive filter). |
| `ATAT1`, `ATSTFF` | Adaptive timing, capped at the longest timeout, `AT ST FF` (0xFF x 4 ms). Adaptive timing is turned off again when the driver paces the module (Timing). |

Commands with a single non-hex letter (`ATE0`, `ATCAF1`, `ATCF700`) are left out for the bit-flip reason under Safety.
Echo, CAN auto formatting and CAN flow control stay at their defaults (on), which is why the driver reads the `AT PPS`
summary and refuses an adapter that changed them (PP 09, 24, 25 and 29; Safety). After the setup, `STI` tells an STN
chip from a clone: only an answer starting `STN` counts.

## Failure states

After any of these the driver's state is unknown, and every later call fails without writing anything (connect
again):

- the adapter doesn't finish a command in time, or stays quiet in a request for longer than its own timeout plus
  `SILENCE_MARGIN` (6 s; Timing);
- it refuses a setting;
- it echoes a line other than the one written (Safety). On an adapter that echoes whole lines only, a request it
  misheard has gone on the bus by the time the echo shows it;
- it prints something unexpected: an overlong line, `STOPPED` outside an interrupt, a frame from outside its receive
  filter or of the other ID width (with headers off, a line of five or more bytes can read like a 29-bit frame), or
  anything between its prompt and the next line it's sent;
- it says it reset (`LV RESET`, `ERRxx`, `LP ALERT`, a banner) or is searching for a protocol (`SEARCHING...`,
  `UNABLE TO CONNECT`);
- the link fails.

`connect` also refuses an adapter whose programmable parameters turn off echo, CAN auto formatting or CAN flow
control, or turn on the CAN data length display.

## Events and dropped replies

Replies still arriving when the next request is sent are dropped, after being checked for signs of a reset. They
aren't returned, as that would let a late reply to a repeated request pass for a fresh one. Their lines are reported
as `LinkEvent::Unread`, and status lines such as `NO DATA` as `LinkEvent::Status` (read or not). `Audited` logs these
and every command sent to the adapter (`Transport::take_events`); dropping the wrapper reads what's left of the last
request first (`Transport::settle`). At most `MAX_EVENTS` (4096) events are kept until taken, and `LinkEvent::Lost`
counts the rest. Multi-frame replies are reassembled per module for up to 16 modules per request; frames from any
more are dropped, so those modules' replies time out.

## Flow control per target

`set_target` picks the flow control before each request whose target changed it:

| Target | Flow control |
|---|---|
| Broadcast 0x7DF | Mode 0, the adapter's own. Never paced. |
| Physical 0x7E0..=0x7E7, not paced | Mode 0. |
| Physical 0x7E0..=0x7E7, paced | Mode 1, to the request ID, with the STmin from Timing. |
| Any other physical module | Mode 1, to the request ID. |
| Any 29-bit request | Mode 1, to the request ID, since mode 0 swaps the reply ID's bytes (Safety). |
| Raw TP2.0 frame | None; whatever was set stays. |

Mode 1 sends `30 00 xx` (continue, no block limit, gap `xx`). `AT FC SD` keeps two non-hex letters (`T`, `S`), so one
flipped bit can't make it a bus request. A broadcast can't be paced because each answering ECU needs flow control on
its own request ID, which only mode 0 provides; `scan` and `fingerprint` avoid it for long replies where the driver
paces (Timing). The adapter answers any first frame its receive filter shows, so the
narrow filter also keeps another module's long reply on a busy bus from being acknowledged in the tester's name.

## VW TP2.0 channel frames

- **TP2.0 frames go out raw.** For a channel setup or disconnect the policy built (`Protocol::Tp20Channel`), the
  driver switches the adapter with four commands, and back with four more before the next ISO-TP request. On an
  adapter that isn't paced it also turns adaptive timing off after the fourth (`AT AT0`) and back on after the last
  (`AT AT1`), below:
  - `AT CFC0` first, `AT CFC1` last: automatic flow control answers any frame that looks like an ISO-TP First Frame
    (`1x`), whatever `CAF` is (p. 14). A TP2.0 frame can start that way, and the flow control would be an
    unapproved frame on the bus.
  - `AT V1`, then `AT V0`: even with `CAF0` the adapter pads every frame to 8 bytes (p. 46) unless variable DLC is
    on (p. 27; the OBDLink FRPM says the same). A setup is 7 bytes and a disconnect 1.
  - `AT CAF0`, then `AT CAF1`: no ISO-TP length byte is added to a request or stripped from a reply (p. 13), so
    each line of digits is one frame's data (up to 8 bytes), and each reply line is one frame.
  - `STCMM 1`, then `STCMM 0` on an STN, `AT CSM 0`, then `AT CSM 1` on any other adapter: whether the monitor
    below acknowledges the frames it hears. The adapter acknowledges frames while it listens after a request, but
    its monitor is silent on the bus by default (`STCMM 0`; `AT CSM 1`). Behind the gateway the diagnostic bus has
    two nodes, the module and the adapter, so a module's frame that nobody acknowledges is sent again and again,
    and the adapter reports `CAN ERROR`: car session 9 saw a module's `300 10 00 03 7F 1A 11` printed 31 times,
    then `CAN ERROR`, and the answer was lost (#301). `STCMM 1` is "normal node, with CAN ACKs" (OBDLink FRPM,
    section 8.8); an STN lists `AT CSM` as deprecated there. An ACK is a bus-level bit, not a frame: it carries no
    data and asks nothing of a module, and the adapter already sends it in every listen after a request. It is
    sent once, with the other switches, so nothing sits between a module's ACK and its answer; leaving raw mode
    puts the silent default back, so a future listen-only monitor (#104) starts silent. An adapter that refuses
    it (`?`, such as a clone without `AT CSM`) fails closed with an error naming the setting, before any channel
    frame goes out: a monitor that stays silent can't hear a module's answer.
  - `AT AT0`, then `AT AT1`: a learned timeout from the fast setup and parameter replies (about 45 to 80 ms) made
    the adapter print its prompt right after a module's ACK, long before the session's own wait for the data frames
    ran out (#218). A paced adapter has adaptive timing off already and is sent neither. The driver keeps one rule
    for `AT AT0`/`AT AT1` (adaptive timing on only when the adapter isn't paced, isn't in raw mode and isn't in a
    patient window), so a patient window that opens while raw mode is still on from an earlier channel, or closes
    before it ends, doesn't undo the other.
- **The switch commands are written like requests.** `AT CAF0`, `AT CAF1`, `AT CFC0` and `AT CFC1` have no non-hex
  letter but the `T` of `AT`, so one flipped bit could make them a bus request. The driver writes each command's
  characters, checks the echo, and only then writes the carriage return, or ends the line with `XX` on a mismatch
  (above); `AT V0`, `AT V1` and the ACK setting (two or more non-hex letters) go the same way. That only works on an adapter that echoes each character as it
  reads it, so raw mode needs one that has shown it does on an earlier ISO-TP request (the OBDLink EX does). On any
  other adapter the driver refuses to send a TP2.0 frame, and `scan --discover-tp20` runs after the scan's ISO-TP
  reads for this reason. Tests flip every bit of each character of all eight commands, with either ACK setting, and of `AT AT0` and `AT AT1`;
  the carriage return is written only after their echo checks out. (Those two have a second `T`, so a flipped bit
  couldn't make them a bus request anyway; a patient window that opens before any request has shown the echo
  sends them as ordinary settings.)
- **An ACK can't wait for the prompt.** After each frame it sends, the adapter listens for its whole timeout
  (`AT ST`, about 1 s) before printing its prompt, but a module waits only its T1 (about 100 ms) for the tester's ACK.
  So a frame on an open channel (`Target::Tp20Channel`) sent while the adapter still listens first stops it: the
  driver writes `X`, which the adapter discards (p. 7), and reads up to `STOPPED` and the prompt. Lines read on the way
  that nobody took are logged as unread. Before writing it, the driver reads what's already on the link, and if the
  prompt is there, nothing is interrupted.
- **An interrupt that crosses the prompt is refused.** If the timeout runs out just as `X` arrives, the prompt comes
  without `STOPPED` and `X` starts a new line; the driver ends it as `XX`, which the adapter refuses with `?`. No single
  flipped bit of `X` or of `X\r` makes a hex digit, so neither can become a bus request (tests flip every bit).
- **Frames between the prompt and the next line are lost, so the driver listens by monitoring.** The adapter only
  prints frames while it listens after a request, and an STN ends a raw listen with its prompt after the first frame
  it prints (car session 8 saw it after every frame on a channel, #227; the OBDLink manual says it should wait for the
  next frame, and nobody knows the rule, [design](design/tp20-stn-listen.md)). A module that ACKs the tester's frame
  and sends its answer a few milliseconds later would have that answer lost, and the session closes the channel
  rather than read an answer wrong. That is what car session 11 showed on the A7's modules 52 and 20 (#333): the
  STN's prompt after the ACK, then the echo round trip of `STM` (a setting command takes 15 to 17 ms on this adapter),
  and the module's first data frames are gone. On an STN that takes batched commands the frame and `STM` go as one
  line, so there is no gap (below). Otherwise, when the prompt comes during `recv` after a frame on an open channel
  (`Target::Tp20Channel`), before the caller's wait has run out, the driver at once starts monitoring the bus and
  goes on returning frames until the wait ends:
  - The command is `STM` on an STN and `AT MA` on any other adapter. It must be `STM` on an STN: its `AT MA` and
    `STMA` switch to a pass-all filter whatever `AT CRA` says (OBDLink FRPM, section 7.3), where `STM` "uses the
    filters as set" (section 8.9), so `AT CRA 300` (the module's channel ID) still holds. On an ELM327 `AT MA` honors
    `AT CRA` on CAN (ELM327DS p. 20). A frame from any other ID is still refused (above). A monitor sends no
    frame, but it acknowledges the frames it hears (`STCMM 1`, `AT CSM 0`, above): silent, it leaves a module's
    answer unacknowledged, and the module repeats it until the adapter says `CAN ERROR` (#301).
  - It's written like the other mode switches (echo checked before the carriage return; `STM` and `ATMA` hold two or
    more non-hex letters, so no single flipped bit makes a bus request) and logged as a command. Every frame it
    prints is logged like any other reply.
  - A monitor prints no prompt, so the silence watchdog doesn't apply to it: the caller's wait bounds it, and
    stopping it is bounded by `COMMAND_WAIT`. A prompt it prints on its own, which the driver finds before it has written
    the stop character (in a wait, or while a send, command or `settle` stops it), is unexpected output and fails the
    adapter closed.
  - Anything written next stops it first, as it stops a listen (`X`, then `STOPPED` and the prompt, above): the next
    frame on the channel (an ACK, `A3`, `A8`), an ISO-TP request, a command, or `settle`. Frames it printed that
    nobody read by then are logged as unread. `BUFFER FULL` from a monitor fails the transfer (`recv` fails at once;
    a stop reports it after the monitor has stopped, and the frame isn't sent).
  - Nothing else monitors: a channel setup (`Target::Tp20Setup`) and ISO-TP requests end at the prompt as before.
  - **Batched `<frame>|STM`, on an STN that takes `STBC 1`** (#333, [design](design/tp20-stn-listen.md)). An OBDLink
    can run several commands from one line, `|` between them, under one prompt (FRPM rev. F, sections 8.15 and 16.0:
    "Commands are processed sequentially from left to right", and "you may safely place ATMA, STMA, or STM at the end
    of the batch"). So the frame and `STM` are one line, and the STN starts monitoring itself when the frame's
    listen ends, with no echo wait or host in between:
    - **Probe.** When raw mode starts, an STN is sent `STBC 1` (after the other switches, written like them), and only
      an exact `OK` turns batching on. Any other answer, `?` included, leaves the old path as it is and `STBC` isn't
      sent again that session. Leaving raw mode sends `STBC 0` if it was turned on, and anything but `OK` fails the
      adapter closed. A plain ELM327 is never sent `STBC`; its byte stream is exactly what it was. Both are logged as
      commands with their answers.
    - **Which frames.** A data frame (opcodes `0x0` to `0x3`) and an ACK (`0xB`): the module answers after its ACK, or
      sends the next block when its ACK goes out. A channel test (`A3`), the parameters (`A0`) and the disconnect
      (`A8`) get one frame back, which their own listen prints, and aren't batched. Everything else, the setup
      included, is as before.
    - **The line.** The frame's digits, then `|STM`, for example `1000021A9B|STM`: the frame is the one the policy
      approved, the digits are the same, and the suffix is a constant. The digits are echoed and checked before `|STM`
      is written, then `|STM` is, then the carriage return. A misheard digit is ended with `XX` into a line that isn't hex
      and nothing is sent; checking the whole line before the pipe would let `XX` end only the last element and the
      damaged digits run as one of their own. A flip inside `|STM`, or one that turns an `M` into a carriage return, can
      leave the checked digits as a complete first element: the approved frame goes out once, `STM` doesn't run, and the
      echo mismatch stops the driver. That error, and a link failure while writing `|STM` or the carriage return or waiting for the echo of `|STM`, say the request *may
      have been sent*, not that it wasn't: only a failure in the digits themselves, ended with `XX` before any carriage
      return, says it wasn't. The channel session passes the error on and never resends the frame. Tests flip every bit
      of the line.
    - **After the carriage return** the driver is monitoring (`monitoring`) and has logged the `STM` as a command, as for a
      monitor it starts itself: once the digits were written and echoed right, before `|STM` was written (a head that
      failed leaves no `STM` entry). The STN prints no prompt between the frame's listen and the monitor. The `|` that
      precedes the monitor's first output (section 16.2.2, verbose output) is taken once, and only in front of the line
      after the frame's own reply (or alone on a line there): once a second line has come without it, a `|` is
      unexpected output like any other. A prompt before the pipe has been seen means the batch ended without its
      monitor (an error before it, or it was dropped): the driver monitors with a plain `STM`, as it does for an
      adapter without batching. A prompt after the monitor's first line, with the pipe in front or without it, is the
      adapter stopping on its own, as for any monitor: a failure, also when `interrupt` meets it.
    - **An `X` while the frame's listen is still running** (a slow module) is assumed, in the worst case, to end the
      whole batch with no `STM`: the driver reads `STOPPED` and the prompt as it does for a listen, and the next frame
      is a new batch. The manual doesn't say what `X` does to a batch ([session 12](design/tp20-stn-listen.md)).
    - **Not verified on hardware**: that the STN2232 (v5.12.4) has `STBC` (rev. F of the manual added it), that a raw
      `CAF0` frame is a valid batch element, where the `|` is printed, what `X` does to a batch, and how quickly the STN
      goes from its listen to `STM`.
  - **Confirmed on the car in session 9** (an OBDLink EX, STN2232): an STN's `STM` prints frames in the same line
    format as after a request with `CAF0` and `ATH1`, `AT CRA 300` still filters it (only the channel's ID printed),
    it prints `STOPPED` on a stop character (section 8.9), and `STCMM`'s default leaves it silent on the bus, which
    is what #301 fixed.
  - **Not verified on hardware yet**: that `STCMM 1` makes the module send its answer once, and that the ACK setting
    is accepted by the ELM327 versions this driver claims to support (`AT CSM` is in the ELM327 datasheet, but a
    clone may refuse it, and then raw mode isn't entered).

  The session (`ChannelSession::request`) sends nothing to make an adapter listen again. It once sent an `A3`
  keep-alive when the adapter's prompt came before its own wait ran out (#218), which put a frame on the channel
  between the module's ACK and its answer; the module may answer a channel test by dropping the channel (#227). It
  still sends `A3` while a module's answer is pending (response-pending or a not-ready ACK), at most
  `Timing::max_pending` times, and before a request after the module's idle time. The fake adapter models the STN's
  one-frame listen, a monitor that takes `monitor_startup` to start and batched commands, and loses a frame arriving
  while neither runs, so the tests can show none was lost. Its module's frames are due from the module's own ACK, not
  from the host's re-arm, which would hide the gap (`docs/pitfalls.md`).
  It is also one of two nodes on the bus: a silent monitor leaves a module's frame unacknowledged, so it prints
  `CAN ERROR` and then the frame 31 times, as in session 9, and an acknowledging monitor prints it once;
  whether real modules answer within these timings is rechecked in car session 9.

## Output format

- With `ATH1` and `ATS1` each received frame is a line: the 3-digit CAN ID, then the data bytes, **PCI byte
  included** (p. 46). With headers off the adapter strips the PCI and prints `0:`, `1:` segment lines instead, so
  the driver turns headers on and reassembles with `obdcracker-core`'s ISO-TP reassembler.
- Replies from several ECUs may interleave (p. 45), so the driver reassembles each CAN ID separately.
- Lines end with a carriage return, plus a line feed if `ATL1` is set; the prompt is `>` (p. 7). The UART may insert
  stray NUL bytes (p. 8).
- Status and error messages are listed on pp. 78-80. A frame that failed a check is printed with ` <DATA ERROR` or
  ` <RX ERROR` after it. An STN also prints `FC RX TIMEOUT` (not in the datasheet): it sent the first frame of a
  multi-frame request and got no flow control (Multi-frame requests). It fails the request and nothing else.

## Timing

- After a request the adapter waits up to `AT ST` x 4 ms for the first reply, and the same again after each reply
  for more (p. 26). The maximum, `AT ST FF`, is about 1 s. With adaptive timing (`AT AT1`, p. 12) the adapter
  learns shorter waits, never longer than `AT ST`.
- The ELM327 v2.0 datasheet says nothing about response-pending replies (`7F xx 78`): such an adapter may stop
  listening after its timeout like after any reply, so a module that takes longer than about 1 s after a
  response-pending reply gets no answer through it. v2.1 and STN chips wait P2* (about 5 s) instead (ELM327DS v2.1,
  p. 90). On the OBDLink EX (STN2232 v5.12.4, #54) the A7's transmission answered 1969 ms after a `7F 19 78`, and the
  answer came through. Either way, `exchange` reports a module that went response-pending and never answered as
  `Error::StillPending` ("said it was busy but didn't answer in time"), not as a plain timeout (#17).
- `AT Z` takes about a second (p. 47).
- The serial link is slow next to the bus: an ELM327 starts at 9600 or 38400 baud (p. 7). A 4095-byte reply is 586
  frame lines of up to 37 characters (29 with an 11-bit ID), about 23 s at 9600 baud, and up to 16 modules can each send one. So the driver
  doesn't bound a request by a fixed time sized for the ECU. A working adapter ends each request with its prompt;
  while it's still printing, the request runs on (up to an outer limit of about 7 minutes, which only an adapter that
  never stops printing reaches). What it does bound is silence: the adapter waits at most `AT ST` for each frame (or
  a patient STN's `STPTO`, below), plus about 5 s after a response-pending reply on v2.1 and STN chips (ELM327DS
  v2.1, p. 90), so an adapter quiet for longer than its timeout plus 6 s mid-request has hung, and the driver stops.
- **Request time limits** (constants in `elm/mod.rs`): `LONGEST_PRINT` is the time to print the longest reply, 4095
  bytes (a first frame and 585 consecutive frames, each a line of up to 37 characters, 10 bits a character) at 9600
  baud: about 23 s. `LONGEST_PRINT_ALL` is that for each of 16 modules, and `LONGEST_REQUEST` (the outer limit
  above, about 7 minutes) adds `STN_LONGEST_TIMEOUT` and a second for the link. `Elm::timing()` gives P2 that value,
  and P2* the default plus `LONGEST_PRINT_ALL`. `SILENCE_MARGIN` is the default P2* (5 s) that v2.1 and STN chips
  wait after a response-pending reply (ELM327DS v2.1, p. 90), plus a second for the link. Silence is the time the
  driver spent waiting, added up across calls, so a caller that reads late or polls with short timeouts doesn't skew
  it; once anything arrives, only the silent tail counts. `ECHO_WAIT` (1 s) is how long a request's digits may take
  to echo before the carriage return: the STN in an OBDLink EX echoes each character within about 15 ms (#54).
- The adapter's transmit buffer is 512 bytes (p. 80). When the bus delivers frames faster than the serial link drains
  them, it fills, data is lost, and the adapter prints `BUFFER FULL`, which the driver reports as an error. So the
  driver paces the module (#23): its flow control asks for a gap between consecutive frames (STmin, ISO 15765-2) of
  the time the adapter takes to print one frame line (29 characters, 10 bits each, or 37 with a 29-bit ID) on the
  link, rounded up to a millisecond. The buffer then never grows. At 9600 baud that's 31 ms (`30 00 1F`), at 38400
  8 ms, at 115200 3 ms; with a 29-bit ID, 39, 10 and 4 ms.
  A broadcast can't be paced (its flow control must be mode 0, above), and several ECUs sending multi-frame replies
  at once on a slow link can overflow the buffer; the error then says `BUFFER FULL` and suggests a faster baud rate
  (PR #70). So where the driver paces (`Transport::broadcasts_can_overflow`: every plain ELM327, at any speed, and an
  STN below 115200 baud), `scan`, `fingerprint` and `read_vin` (the CLI's `vin`) read the long replies (mode 09 PIDs
  02, 04, 06 and 0A, mode 03) from each ECU in turn by its own request ID, which paces them (#71, #242). `fingerprint`
  and `read_vin` first broadcast mode 01 PID 00 to learn the ECUs. If no ECU answers, or the policy gives one of them
  no request of its own on its ISO 15765-4 reply ID (a vehicle profile leaves out its request ID, or gives it another
  reply ID), that read is a broadcast. A broadcast of a long request sent any other way can still overflow.
- A patient read (`Transport::patient`, used by discovery's recheck and wide pass) turns adaptive timing off, then
  back on, so a wait learned from fast modules can't cut a slow one short. When pacing it's already off, so nothing
  is sent, and in raw TP2.0 mode it is off too, so a window opened or closed there sends nothing, and a window open
  when raw mode ends keeps it off until it closes. Each command is sent only when the state changes. That alone doesn't wait any longer for a module that hasn't answered yet: an STN always waits its whole
  timeout for a first reply (STN1100 FRPM), and in #86 every discovery pass waited the same 1.09 s per silent ID
  (#87). So on an STN, patience also sets the timeout itself with `STPTO <ms>` (1 to 65535 ms; `AT ST` is its
  deprecated alias), and restores `AT ST FF` afterwards. A plain ELM327 can't wait longer than `AT ST FF` (about 1 s),
  and discovery says so.
- When it paces, the driver turns adaptive timing off (`AT AT0`) once, after connecting. In raw TP2.0 mode it does the same
  on an adapter that isn't paced (above). The adaptive timer also waits for each next frame
  (OBDLink FRPM) and could learn a timeout shorter than the gap, ending a paced reply early. The timeout is then always
  `AT ST FF`, so each request waits about 1 s after its last reply: a scan on a plain ELM327 is slower, not wrong.
  The link's rate comes from the serial port's baud rate; over Wi-Fi it can't be known (the chip may sit behind its
  own slow UART), so the driver assumes 9600. STmin can't exceed 127 ms, so below about 2300 baud (2900 with a 29-bit
  ID) a long reply can still overflow. An STN chip on a link of 115200 baud or more isn't paced: on the OBDLink EX at 115200 (#49) a
  770-byte reply arrived with no gap and no `BUFFER FULL`. The cost is time: a 4095-byte reply takes 585 gaps,
  about 18 s at 9600 baud (23 s with a 29-bit ID), which is what printing it takes anyway.

## When a reply left the bus

`Response::bus_time` is a time that is never later than the moment the reply's last frame left the bus, which is when
the module restarts S3 (`ExtendedSession` times its session from it, [`scanning.md`](scanning.md#extended-session-and-testerpresent)).
Too early only costs an extra `10 03`; too late would trust a session that may have lapsed. The driver sets it only
where the link has a known byte rate (`Link::byte_rate`: a serial port at its baud rate). Over TCP, and for any link
that states no rate, it is `None` and the session times from the request. Nothing here is a clock on the car: the
adapter timestamps nothing.

For a reply, let L be when its last frame left the bus, P the bytes the link handed over from the request's
final write up to and including the read that ended the reply, and `arrived_after` the earliest the last read's bytes
can have reached the host. The adapter prints from L at its true rate and has no more backlog than P bytes (everything
it printed for the request is in P, other modules' lines included), so the last byte reached the host by L + P / rate +
latency. The driver reports

    bus_time = max(sent, arrived_after - P / (byte_rate / 2) - 100 ms)

which is not later than L provided that:

- the adapter prints at least half of the nominal byte rate on average (`PRINT_RATE_SHARE`); it may leave gaps between
  bytes, and a slower one would make the estimate too late;
- USB latency timers, scheduling and the adapter's own handling of a frame take under 100 ms (`HOST_ALLOWANCE`);
- the request was sent at `sent` or later: the time just before the final write, so the frame left the bus after it.

`arrived_after` is the end of the read that returned the bytes, if that read waited at least a millisecond (so it
returned when they arrived) and began within 100 ms of the link last being drained (the end of the latest read that
got nothing or waited, or the request's send; a short read that got bytes doesn't count, since `Link::read` may return
part of what has arrived). Otherwise it is that drain: bytes found waiting, or read after the caller was away, could
have arrived any time since. A reply read late is so timed no later than when the link was last
drained.

Only the last reply of a request that isn't response-pending is used: `exchange` returns that one, and its `P` includes
the response-pending lines, which only makes the estimate earlier.

What this gets right and wrong:

- Frames that arrive slowly on a fast link (115200 baud, lines seconds apart, or a long response-pending wait and then a
  short answer) get a bus time just before the answer arrived: P is small, so the answer left the bus about when
  it arrived and S3 restarted then.
- A long answer the adapter prints at the link's full speed (a 4095-byte reply at 9600 baud, 18 s) gets a bus time
  before the request, since P / (rate / 2) is longer than the print took. The module may have sent it all at
  once, so its S3 really did run from the start, and the next request enters the session again. A session that
  trusted the end of the print would send reads into the default session.
- When the module paces its frames by the STmin the driver asked for, the last frame left the bus later than the
  estimate says, so the session enters again where it didn't need to. The driver can't tell the two apart.

The module's real S3 is unobserved: whether it restarts on the request, on the answer's last frame, or both, hasn't
been measured on a car. The tests (`bus_time` in `tests/elm.rs`) put a fake link that prints
at a set rate between the driver and the fake adapter, and check both directions: a slow module on a fast link
keeps the session, a long answer printed at the link's full speed doesn't. The gs_usb and SocketCAN backends may set `bus_time` from the
port's hardware timestamps once they exist.

## Receive filter

- By default the adapter picks a receive filter from the header (`AT AR`, pp. 11-12), which the datasheet doesn't
  define for every header. The driver sets its own filter (`AT CRA`, where `X` means any digit, p. 14) before each
  request whose target changed it:
  - the module's reply ID when the approved request carries it (`AT CRA 7E8` for 0x7E0, `AT CRA 77A` for the A7's
    gateway once a profile narrowed the policy);
  - 0x7E0..=0x7EF for an OBD-II broadcast (`AT CRA 7EX`);
  - otherwise every 11-bit ID from 0x700 to 0x7FF (`AT CRA 7XX`, also set at connect), and `exchange` decides which
    replies count;
  - for a 29-bit request, eight digits: its reply ID (`AT CRA 18DAF110`, or a VAG one from a profile), else every
    ISO 15765-4 reply to the tester (`AT CRA 18DAF1XX`) or every VAG one (`AT CRA 17FE00XX`). A 29-bit frame line
    shows its ID as four bytes (`17 FE 00 76 03 62 F1 87`), and a frame of the other width than the filter's always
    counts as one the filter should have hidden.

  `AT CRA` keeps two non-hex letters (`T`, `R`), so one flipped bit can't make it a bus request.

  The driver assumes `AT SH` leaves the filter alone, as the datasheet describes no such reset, and session 2 (#49)
  agrees: with `7XX` set once at connect, the gateway's 0x77A replies still showed after `AT SH 710`. A frame the
  current filter hides means the adapter lost the filter, and the driver stops. `X` digits arrived in ELM327 v2.0 (ELM327DS v2.1, p. 90);
  STN chips accept them too (OBDLink FRPM, `ATCRA pattern`), though they report themselves as v1.4b. A genuine older
  ELM327 or a clone that answers `?` is refused at connect. The older alternatives aren't safe: `AT CF 700` has a
  single non-hex letter, and `AT CRA hhh` + `AT CM 700` leaves an `M` that one flipped bit turns into a carriage
  return.

## Clones

Most ELM327 adapters sold are clones. They often claim a version Elm Electronics never released (`v1.5`) or one they
don't implement (`v2.1`, python-OBD #132, #188), so the driver trusts what an adapter does, never the version it
names. What it does with the clone behaviour seen in python-OBD's tracker (#44), each covered by a fake-adapter test
in `crates/obdcracker-transport/tests/elm.rs` (`clones`):

| Behaviour | Source | What the driver does |
|---|---|---|
| Noise before the banner after `ATZ` (`\xfc\r\rELM327 v1.5`) | python-OBD #205 | Works: it waits for a line starting `ELM327`, then the prompt. |
| `?` to `AT CRA 7XX` (no `X` digits before v2.0) | #132, #188 | **Fatal** at connect: the error names the command, the banner the adapter gave, and what's needed (ELM327 v2.0+ or STN). The older filter commands aren't safe (Receive filter, above). |
| `?` to `AT PPS` | | Works: no programmable parameters means factory defaults. |
| `?` to any other setup command | | **Fatal** at connect, naming the command. Each one sets something a reply or the bus depends on. |
| An answer with no prompt (`ATE0\rOK` and then nothing) | #160, #205 | **Fatal**: "answered … but never printed its prompt". Without the prompt the driver can't tell whether more is coming, and writing over an answer interrupts the adapter. |
| A request answered with an empty line and a prompt (`\r\r>`) | #205 | Works: no reply (`Timeout`), and the adapter stays usable. |
| A link that drops mid-request (Bluetooth SPP) | #188 | **Fatal**: the error names the link (`usb-serial link: …`); connect again. |
| A slow baud rate (38400, 9600) | #188, #201, #218 | Works with `--baud`; long replies are paced to the link (Timing). `scan`, `fingerprint` and `vin` read them per ECU. |

A missing prompt is never taken as the end of an answer: the driver waits for the prompt, and an adapter quiet for
too long mid-request fails closed (Timing).

## Multi-frame requests

An STN chip sends a request longer than one frame with `STPX` (OBDLink FRPM rev. F, section 8.6, p. 36 of 78: "STPX
param1 [, ..., paramN]"): "transmit arbitrary message on OBD bus", with `d:<hex>` for the data, and optional `h:`
(header; omitted, the `ATSH` one is used), `t:` (response timeout; omitted, `STPTO` is used, and `ATAT` is still
obeyed), `r:` (response count), `x:` (ISO 15765 extended address) and `l:<len>` (data sent on a separate line after a
`DATA>` prompt). It turns segmentation on for that message only. The manual's maximum message size is 4 KB on the
OBDLink MX+ and 2 KB on the other devices, and it doesn't say how `STPX` echoes or prints replies. An OBDLink EX
(STN2232 v5.12.4) was checked on the A7 with the engine off, and the fake adapter models what it printed (#215, [results
comment](https://github.com/DaSonOfPoseidon/OBDCracker/issues/215#issuecomment-6768155029)): the `STPX d:` line is echoed
like any other request, and the reply comes on its own line after the echo.

- **The `d:` form, one line, headers and timeout left to the existing settings.** The driver writes
  `STPX d:22F187F188F189F191` (digits without spaces) exactly as it writes a request: without the carriage return,
  checks the whole echo, and only then writes the carriage return. The `l:` form was rejected: its data line is a
  line of hex digits that the manual doesn't say waits for a carriage return (the adapter may count bytes and send at
  the last digit, before the echo can be checked), and a `DATA>` prompt is a second state to get wrong.
- **The guard is the request's.** A mismatched or missing echo writes `XX` and a carriage return, stops the driver
  and sends nothing; the echo of the full line is compared again after the carriage return (`reply_line`). The driver
  sends it only on an adapter that has already shown it echoes each character as it reads it (`early_echo`), and
  refuses otherwise rather than write an unguarded line. It never sends `STPX` to a plain ELM327 (which answers `?`)
  or in raw TP2.0 mode, and the audit log records the request, not the `STPX` line.
- **The kill works.** On the OBDLink EX, `STPX d:0902XX` printed `?` and nothing else: the line is refused whole, like a
  line of hex digits with a stray letter, so a misheard `STPX d:` line killed with `XX` sends nothing. Checked from the
  adapter's reply only, with no second bus monitor (#215).
- **`FC RX TIMEOUT` fails only that request.** After a request of several frames the STN printed `FC RX TIMEOUT`:
  it sent the first frame, no flow control came back in time, and it sent nothing more (`STPX d:22F187F188F189F191` to
  the A7's engine, 7E0, #215). The adapter is back at its prompt with its settings, so `recv` fails with an adapter error
  naming the status and the driver stays usable, as after `CAN ERROR`. Only that exact line is taken this way:
  anything near it (`FC RX TIMEOUTX`) is unexpected output and stops the driver.
- **Limit:** 44 bytes (43 for a `22` read, whose length is always odd: 21 DIDs). The echo of the `STPX d:` line must
  fit one line of the line splitter (96 characters), so the driver's limit is far below the adapter's.

## Multi-frame requests on a plain ELM327

A plain ELM327 has no `STPX` and sends one frame per request line, so the driver writes the ISO-TP frames itself, with
CAN auto formatting off (`AT CAF0`). The [design note](design/elm-caf0-segmenting.md) has the reasoning, the datasheet
pages and every bound; this is what the driver does.

**Datasheet only.** Nothing here has run on a plain ELM327 or a clone: the only hardware so far is an OBDLink EX, an
STN, which takes `STPX` instead. `Elm::segment_on_stn(true)`, or `--elm-segmenting caf0` on the CLI, makes an STN take
this path too (#308, below). The note's Open questions 1 lists what a plain
ELM327 could still falsify. It is on for plain ELM327s anyway (the user's call, 2026-11-10), because every way it can
fail is closed: a refusal, a failed request, or a stopped driver.

- **When.** A request of 8 to 44 bytes to one module with a known reply ID (`Approved::reply_id`), 11- or 29-bit,
  normal addressing, on an adapter that isn't an STN and has shown it echoes each character as it reads it. A request
  to a module with no known reply ID (a broadcast, or a physical ID the policy wasn't narrowed to), one of 45 bytes or
  more, and one on an adapter whose `AT PPS` summary doesn't list PP 26 are refused before a byte is written. Extended
  addressing (#112) has no `Target` yet, so nothing can ask for it.
- **Frames.** From core's `isotp::Segmenter`, padded to 8 bytes by the driver with the adapter's own filler byte
  (PP 26, `00` by default), and written one line each, like a request: the 16 digits, their echo checked, then the
  carriage return. A mismatch ends the line with `XX`, which the adapter refuses, and stops the driver.
- **Order.** `AT CAF0` before the first segmented request (and `AT CAF1` before the next request that isn't one, so a
  run of segmented reads pays for the switch once). The first frame with `AT R1`; the module's flow control read, with up
  to 10 wait frames before it; `X` to stop the adapter's listen; then each consecutive frame, with `AT R0` while more
  follow in the block (the adapter then returns to its prompt at once instead of listening for a second) and `AT R1`
  before the last frame of a block. No consecutive frame goes out before a flow control.
- **Bounds.** At most 7 frames, 500 ms between two frames (`SEGMENT_GAP`: a later frame is killed, not sent), 30 s in
  all (`SEGMENT_TRANSFER`), and the flow control's STmin between consecutive frames, kept to the millisecond (100 to
  900 µs rounds up to 1 ms). A failure sends nothing more, puts `AT R1` back, and the driver writes nothing for 1.25 s
  (`SEGMENT_HOLD`), so the module drops the half transfer first.
- **Reply.** Read as for any request: the adapter's own flow control answers a multi-frame reply, to the request ID
  (`AT CFC1` and `AT V0` stay as they are, so this isn't TP2.0's raw mode). `CAF0` also prints a frame with an invalid PCI
  byte, which is dropped (the request times out), and a remote frame as `RTR`, which stops the driver as unexpected
  output.
- **Audit log.** The request once, before anything is sent; then each frame written (`"dir":"tx_frame"`, noted when its
  carriage return is written) and each flow control read (`"dir":"rx_frame"`), with `AT CAF0`, `AT R0`, `AT R1` and `X`
  as commands between. A line that was killed is a command, not a frame. A line the adapter prints besides the flow control (`NO DATA`, `BUS BUSY`, a
  frame the module sent after its flow control) is reported as a status or unread line, even when the request fails on
  it. A frame the module sends while the adapter isn't listening (`AT R0`) is lost and not logged.
- **Forcing it on an STN** (#308). `Elm::segment_on_stn(true)` makes a request of 8 to 44 bytes on an STN take this path
  instead of `STPX`, with every check above (the early echo, a known reply ID, PP 26); 1 to 7 bytes stay one frame, and
  off (the default) is exactly the `STPX` path. A plain ELM327 takes this path whatever it is set to. Each call adds a
  `LinkEvent::Setting` named `segment-on-stn` (`"on"` or `"off"`), whatever the adapter, which an `Audited` opened
  afterwards logs first, as `"dir":"setting"`, before any request. The CLI sets it with `--elm-segmenting caf0`
  ([usage](usage.md#sending-a-long-request-on-an-stn---elm-segmenting)). What an STN does differently here is still
  unknown until the car ([design](design/elm-caf0-segmenting.md), Open questions 3).

## Limits

- Without `STPX` or segmenting, with auto formatting on, a request is one single frame of up to 7 bytes (p. 46). The
  driver refuses longer requests before writing anything on an adapter that hasn't shown it echoes as it reads, and a
  plain ELM327 sends them in segments (above). That covers the OBD-II reads and UDS 0x22 with up to 3 DIDs in one frame,
  and 0x22 with 4 DIDs (9 bytes) in segments. A scan still batches at most 3 DIDs, so any adapter can run it
  (docs/scanning.md).
- The A7's engine (7E0) sent no flow control for a multi-frame request, so the four-DID read `22 F187 F188 F189 F191`
  got `FC RX TIMEOUT` and no answer (#215). Why isn't known yet (#306); until then a scan's batches stay at 3 DIDs.
- A first frame's 12-bit length allows replies of up to 4095 bytes (p. 46).
